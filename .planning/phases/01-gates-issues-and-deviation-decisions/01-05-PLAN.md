<objective>
Retire the legacy issue tooling: decide what happens to the `issues/272/` analysis, delete
the `issues/` directory from the working tree, and remove its `.gitignore` rule.

Purpose: D-05 replaces `issues/create_issues.sh` with `scripts/create-property-issues.sh`
(plan 01-04). Leaving the old script on disk leaves two sources of truth for issue bodies
with two incompatible label schemes.
Output: one `.gitignore` hunk and one local filesystem deletion.
</objective>

<blocker_note>
**Research B-1 (verified this session): `issues/` is gitignored and untracked.**
`.gitignore:25` contains a bare `issues/` line; `git ls-files issues/` returns zero files;
`git check-ignore -v` confirms all three entries are ignored.

Consequences this plan is built on, and which the reviewer must not read as scope drift:
1. "Delete `issues/` in PR A" **produces no diff hunk.** A verifier looking for the deletion
   in the PR A diff will not find one. The deletion is verified on the filesystem
   (`test ! -e issues/`), not in git.
2. The **reviewable artifact is the removal of the `issues/` line from `.gitignore`.** That
   is a real hunk, it is the evidence the old tooling is retired, and it stops a future
   `issues/` directory from being silently ignored.
3. `issues/272/` currently contains only `README.md`; the seven `.lean` files its table
   describes are already gone, and its `lake env lean issues/272/<File>.lean` instructions
   cannot work.
4. Nothing under `scripts/`, `.github/`, `docs/` or `package.json` references any `issues/`
   path. The repo-wide `grep -rn "issues/"` hits are GitHub URLs only.

This plan is sequenced after plan 01-03 (which owns the other two `.gitignore` edits) so
that the file has a single owner per wave, and it performs the deletion and the ignore-rule
removal **in the same task** so the untracked directory never sits un-ignored in
`git status`.
</blocker_note>
