  <action>
    Write `docs/rubrics/spqr-statement-review.md`. The reviewer is given one property: its ID,
    its proposed Lean statement (verbatim, as it will appear in the file), its catalog text,
    and **only** its cited source - the spec section, the SCKA reference, or the code lines.
    Not the rest of the catalog, and not the proof.

    It rules on four things:
    1. **C2 - faithfulness.** Does the statement say what the cited source says? The failure
       modes to hunt: a statement stronger than the source (proves something unclaimed), a
       statement weaker than the source (a vacuous or near-vacuous postcondition), a statement
       about a different function than the source describes, and a statement whose
       quantifiers do not match the source's scope. Require the reviewer to quote the source
       text and the statement side by side.
    2. **C1 - novelty.** Is there already a theorem for this on `main`? A statement that
       restates an existing lemma under a new name is a REJECT.
    3. **C3 - band.** Does the statement range over what its claimed band says? A statement
       claiming the refinement band while quantifying over one call is misbanded.
    4. **Vacuity.** For a WP-style statement `f args ⦃ r => P r ⦄`, could `P` hold trivially -
       because the postcondition is implied by the types, or because the precondition is
       unsatisfiable? This is the single most valuable check, because a vacuous spec passes
       every gate this project has.

    Verdict vocabulary: **ACCEPT** (statement may enter proof work as written),
    **REVISE** (specific wording change required; re-review after), **REJECT** (not a valid
    target: invented, duplicate, misbanded or vacuous). Plus **HUMAN_RULING** when the
    reviewer's objection turns on what the source means rather than on what it says.

    **What the reviewer is given, precisely.** Not prose — a **statement record**: one file
    per obligation under `docs/statements/<ID>.md`, holding the complete proposed Lean
    declaration in a single fenced ```lean block, with the namespace, the argument types and
    every hypothesis written out as they will appear in the file. The record also names the
    extracted declarations it is about (`SrcTranslated/Funs.lean` / `Types.lean` by name and
    line) so the reviewer can type-check the statement by reading. Prose questions are not
    reviewable and cannot be hashed to anything that identifies the eventual theorem — that is
    the defect this format exists to prevent. Write `docs/statements/README.md` defining the
    format and stating that the SHA is taken over the fenced block alone, so surrounding
    commentary can be edited without invalidating an ACCEPT.

    **The C1 evidence channel, and the revision it is taken from.** A reviewer given only the
    cited source cannot rule on "is this already proved on `main`", so the packet carries one
    more item: a name-and-signature search for the functions the statement mentions —
    declaration names, signatures and `file:line`, and nothing else. No proof bodies, no
    neighbouring catalog rows.

    **That search runs against an explicitly resolved `main`, not the working tree.** C1 says
    "no theorem on `main`" (`PROJECT.md` § Target Selection), and the two differ here: on
    2026-09-15 `origin/main` was `e8f6689` and carried
    `Spqr/Specs/Chain/Chain/EpochIdx.lean` with a proved `epoch_idx_spec` — a **file the
    working tree does not have** — so a working-tree search would have certified PROP-29 as
    novel when `main` already proves it. Resolve `BASE=$(git rev-parse origin/main)` after a
    `git fetch`, search that revision (`git grep <pattern> $BASE -- Spqr/Specs`), and record
    the SHA and the search patterns in the packet and in the review artifact's provenance
    header. Working-tree extraction evidence may be included too, but must be labelled
    separately so it is not read as the C1 baseline. If the extract or its SHA is missing, the
    reviewer must not return ACCEPT — a C1 ruling with no dated C1 evidence is the failure mode
    here.

    The same baseline governs `docs/proof-targets.md`: classify C1 against that SHA and record
    it at the top of the table, so a later reader can tell what "not already proved" meant.

    **Support-lemma mode.** An excluded-band support lemma still needs its statement checked,
    but C1 and C3 are meaningless for it: it is in an excluded band by definition, and it may
    legitimately restate a neighbouring fact. Define a reduced rubric run — **C2 faithfulness
    and vacuity only**, verdict recorded with an explicit `scope: support` marker — so support
    work has a review route without being promoted to a phase goal. `PROJECT.md` permits
    support lemmas to be proved when a target needs them, and without this mode the checklist's
    "no proof work without an ACCEPT" rule would make them unprovable.

    Output contract, mirroring the plan-review rubric: a header block with property ID, source
    cited, date and a single `VERDICT:` line; a findings section; and a probe log of every
    command run.

    Then write `docs/spec-review-log.md`: a short header defining the entry shape, and a table
    with columns `Property | Obligation | Scope | Statement SHA | Source cited | Reviewer |
    Date | Verdict | Artifact` — `Obligation` because the unit of review is the obligation and
    a row may have two, and `Scope` because a support-mode verdict (`support`) must not read as
    a full target ACCEPT (`target`). `Statement SHA` is `sha256` of the exact statement text reviewed - so an ACCEPT
    cannot be silently reused for an edited statement, which is the loophole a
    property-name-only log would leave. Document how to compute it. Add the header row and one
    worked example row marked as an example.
  </action>
